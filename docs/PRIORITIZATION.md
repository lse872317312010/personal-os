# 需求优先级方法

状态：M0 方法草案。用于比较候选需求，不直接决定 MVP。

## 1. 为什么不直接使用功能投票

Personal OS 的首位用户是创建者本人，且部分需求来自长周期、敏感数据和跨领域协同。单纯按“想要程度”排序会忽略证据质量、闭环价值、验证速度和风险。

## 2. 评分维度

每项使用 0–3 分：

| 维度 | 0 分 | 3 分 |
|---|---|---|
| 痛点强度 P | 很少发生或影响轻微 | 高频且明显损害结果 |
| 闭环贡献 L | 只增加展示或文本 | 补齐基线—行动—反馈关键断点 |
| 跨域复用 X | 单一特殊场景 | 多个领域共同需要 |
| 证据强度 E | E0 | E3 |
| 可验证性 V | 难以观察结果 | 一个有限周期内可验证 |
| 学习价值 K | 不影响后续决策 | 能显著降低 MVP/架构不确定性 |
| 实施/操作负担 B | 低 | 高 |
| 风险与隐私成本 R | 低 | 高 |

候选优先级：

`Score = 2P + 2L + X + E + V + K - B - 2R`

该公式只用于暴露权衡。分数不能覆盖安全硬约束，也不能替代用户对方向的决定。

## 3. 入选 MVP 的硬门槛

需求即使得分高，也必须满足：

- 能追溯到真实场景或被标记为验证实验；
- 有明确的完成和失败判据；
- 数据与行动风险存在可接受控制；
- 不依赖尚未决定的完整平台能力；
- 能服务至少一个端到端闭环；
- 不违反成年人、合法、自愿、隐私和反操纵边界。

## 4. 首轮评审集合

优先评分以下需求，而不是一次评估全部 backlog：

- 基线与事实/推断分离：`SYS-001`、`SYS-003`、`APP-001`；
- 机会排序：`SYS-004`、`APP-003`；
- 行动与反馈：`SYS-002`、`SYS-007`、`APP-004`；
- 用户纠错与审计：`APP-006`、`NFR-002`；
- 敏感数据控制：`SYS-005`、`APP-007`、`NFR-004`。

## 5. 评审输出

每次优先级评审必须保存：

- 各维度分数与依据；
- 使用了哪些来源和假设；
- 哪些需求因硬门槛被排除；
- 前 3–5 项如何组成完整闭环；
- 哪项新证据最可能改变排序；
- 用户接受、修改或拒绝了什么。
