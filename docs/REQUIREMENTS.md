# 需求基线草案

版本：`0.1-draft`  
阶段：M0 / 未冻结

## 1. 证据与状态约定

### 证据等级

- `E3 已确认`：用户明确表达并在当前项目上下文中重复确认；
- `E2 已有上下文`：来自既有对话总结或稳定项目记忆，但仍建议回看原始材料；
- `E1 工作假设`：合理推导，尚未得到用户确认；
- `E0 待探索`：问题已识别，但没有足够依据形成假设。

### 需求状态

`candidate → validated → accepted → frozen`，或进入 `rejected / deferred`。

当前全部需求均为 `candidate`，不得视为冻结范围。

## 2. 系统级候选需求

| ID | 候选需求 | 证据 | 初步验收方式 |
|---|---|---:|---|
| SYS-001 | 系统应保存可纠错、带时间语义的个人状态，而不是把一次判断永久当作事实 | E2 | 用户可查看、修改、废弃状态；历史变化可追溯 |
| SYS-002 | 系统应统一表达目标、约束、优先级、计划、任务和结果 | E2 | 一个目标能追踪至任务、执行记录和复盘结论 |
| SYS-003 | 系统应区分用户陈述、观察事实、外部证据、模型推断、建议和未知项 | E3 | 任一高影响建议可查看其信息类型和来源 |
| SYS-004 | 建议应可转化为具体行动，并有成本、周期、风险和验证指标 | E2 | 建议能生成可执行计划且在周期结束后复盘 |
| SYS-005 | 用户应控制敏感数据的采集、使用、共享、修订、导出与删除 | E3 | 每类敏感数据都有用途、权限、保留和删除规则 |
| SYS-006 | 系统应支持跨领域目标与约束冲突检测 | E2 | 能识别至少一种时间、预算、健康或恢复冲突 |
| SYS-007 | 系统应支持长期反馈驱动的个性化，并避免只重复生成文本 | E2 | 后续方案能引用反馈并解释发生了什么调整 |
| SYS-008 | 高风险或不可逆行动应设置人工确认或专业升级点 | E3 | 风险分级能决定建议、确认、拒绝或转介行为 |

## 3. 外形优化候选闭环

候选流程：

`建立基线 → 明确目标形象 → 分维度诊断 → 机会排序 → 形成行动计划 → 记录执行 → 阶段复盘 → 更新个人模型`

| ID | 候选需求 | 证据 | 初步验收方式 |
|---|---|---:|---|
| APP-001 | 支持从照片、文字资料和用户自述建立带日期的外形基线 | E2 | 基线标明来源、日期、质量限制和用户确认状态 |
| APP-002 | 将面部、皮肤、发型、体态、身材、穿搭和整体表达拆分分析 | E2 | 输出分维度结论，同时保留整体一致性判断 |
| APP-003 | 对改善机会按影响、成本、周期、风险和可逆性排序 | E1 | 用户能理解排序理由并调整权重 |
| APP-004 | 将改善建议转成阶段计划和可追踪任务 | E2 | 每项行动有频率、完成条件和复盘日期 |
| APP-005 | 区分审美偏好、可观察特征和健康相关判断 | E3 | 不把偏好包装成客观缺陷；健康风险触发边界提示 |
| APP-006 | 支持用户否定结论、补充上下文并触发重新评估 | E2 | 纠错后旧推断不再被当作当前事实使用 |
| APP-007 | 对敏感照片采用最小保留和明确用途策略 | E3 | 未经明确需要不持久化原图；派生信息可审查和删除 |

## 4. 健身与身体状态候选闭环

候选流程：

`建立身体与训练基线 → 明确目标与偏好 → 生成周期计划 → 记录训练和恢复 → 识别偏离与风险 → 周期复盘`

| ID | 候选需求 | 证据 | 初步验收方式 |
|---|---|---:|---|
| FIT-001 | 支持记录体重、围度、体态、训练经历、可用器械和时间等带日期的基线 | E2 | 每项记录有来源、日期、单位和可信状态 |
| FIT-002 | 训练目标应同时表达期望结果、训练偏好、明确不练项目与现实约束 | E2 | 计划不因通用模板覆盖用户明确偏好和限制 |
| FIT-003 | 训练计划应包含动作、负荷/强度、组次、频率、进阶条件和停止条件 | E1 | 任一任务可执行、可记录，并知道何时调整或停止 |
| FIT-004 | 系统应记录完成度、主观用力、疼痛/不适、睡眠和恢复等反馈 | E1 | 计划调整能引用实际训练与恢复记录 |
| FIT-005 | 系统应区分健身建议、康复建议和医疗判断 | E3 | 疼痛、受伤或异常信号触发暂停与专业升级边界 |
| FIT-006 | 评估结果应考虑测量噪声和观察周期，不因单次波动重写长期判断 | E1 | 体重等波动指标使用趋势与复核规则 |
| FIT-007 | 健身目标应能与饮食、外形、时间和恢复约束协同 | E2 | 至少能识别一种热量、恢复或时间冲突 |

## 5. 饮食与营养候选闭环

候选流程：

`建立饮食与身体目标 → 识别营养和行为差距 → 形成可执行饮食策略 → 记录依从性与身体反馈 → 调整`

| ID | 候选需求 | 证据 | 初步验收方式 |
|---|---|---:|---|
| NUT-001 | 支持记录饮食目标、身体目标、过敏/不耐受、健康约束、预算、时间和食物偏好 | E2 | 饮食方案可追溯到目标与限制，禁忌不会被推荐 |
| NUT-002 | 系统应允许不同记录精度：完整称重、估算、模板餐或仅记录关键行为 | E1 | 用户可在负担与精度间选择，并明确误差影响 |
| NUT-003 | 饮食建议应给出目标区间、替代方案和最小可执行版本 | E1 | 用户无法执行原方案时仍有符合约束的替代项 |
| NUT-004 | 系统应联合训练、体重趋势、饥饿感、消化、睡眠和依从性调整策略 | E1 | 调整理由引用多日趋势，不只依赖单次记录 |
| NUT-005 | 系统不得把一般营养建议包装成疾病诊断或治疗 | E3 | 涉及疾病、药物、进食障碍等情况时触发专业升级 |
| NUT-006 | 评价饮食方案时应同时考虑效果、可持续性、成本和生活摩擦 | E2 | 复盘不只评价热量或体重单一指标 |
| NUT-007 | 饮食数据应按健康相关敏感数据处理，并允许低粒度长期保留 | E2 | 用户能选择保存原始日志、摘要趋势或不保存 |

## 6. 社交与关系候选需求

关系模块以 `V × T × A × M` 作为分析框架，不作为人的单一价值评分：

- `V`：个人综合价值；
- `T`：有效社交流量池；
- `A`：可得性与接触机会；
- `M`：双向匹配程度。

| ID | 候选需求 | 证据 | 初步验收方式 |
|---|---|---:|---|
| REL-001 | 支持分别分析 V、T、A、M 的瓶颈，避免把问题归结为单一分数 | E3 | 输出能说明主要瓶颈和证据，不产生“总人格分” |
| REL-002 | 所有建议仅适用于成年人、合法且双方明确自愿的互动 | E3 | 违反边界的目标或行动不进入计划 |
| REL-003 | 系统不得建议欺骗、操纵、胁迫或侵犯隐私的策略 | E3 | 风险规则能够拒绝此类行动并说明原因 |
| REL-004 | 关系结果应以双向匹配和长期质量衡量，而不只看接触数量 | E2 | 复盘包含双方意愿、匹配质量和边界体验 |
| REL-005 | 支持记录社交目标、场景偏好、时间预算、边界与不可接受行为 | E2 | 建议不违反用户边界，且能解释适用场景 |
| REL-006 | 支持将 V、T、A、M 中识别的瓶颈转化为低风险、可复盘的实验 | E1 | 实验有目的、周期、停止条件和结果记录 |
| REL-007 | 系统应把第三方资料限制在完成当前目标所需的最少范围 | E3 | 不建立未经同意的第三方长期画像或敏感推断 |
| REL-008 | 对外发送信息、发布内容、预约或关系推进动作必须逐次或按明确规则授权 | E3 | 没有有效授权时只能生成草案或建议，不得执行 |
| REL-009 | 系统应支持记录用户主观体验、边界感受和双向反馈，而非只优化转化率 | E2 | 复盘包含舒适度、尊重和长期质量指标 |

## 7. 非功能候选需求

| ID | 候选需求 | 证据 | 初步验收方式 |
|---|---|---:|---|
| NFR-001 | 可解释：高影响输出应给出依据、置信度与未知项 | E3 | 用户能够追溯结论形成过程 |
| NFR-002 | 可审计：关键数据和决策变化应有历史 | E2 | 能回答“何时、为何、由谁改变” |
| NFR-003 | 可迁移：用户数据不应被单一模型或供应商锁死 | E2 | 定义可读的导出边界，具体格式留待 M2 |
| NFR-004 | 最小权限：模块和 Agent 只访问完成任务所需数据 | E3 | 权限可按领域、数据类型和动作表达 |
| NFR-005 | 可降级：模型或外部服务不可用时不应破坏已存个人记录 | E1 | 核心资料仍可读取、导出和纠错 |

## 8. 当前缺口

- 需要回看 2026-08-17 原始对话，为 APP 系列需求建立逐条来源；
- 健身、饮食和关系候选需求主要来自项目方向与通用闭环，仍缺少逐条真实使用证据；
- 尚未确定 MVP 是优化分析质量，还是优先验证行动—反馈闭环；
- 尚未定义“有效改善”的指标组合和观察周期；
- local-first 边界、长期记忆生命周期和 Agent 权限仍待决策。
