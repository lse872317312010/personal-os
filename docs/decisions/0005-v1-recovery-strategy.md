# 0005 — v1 采用用户控制的离线恢复包与可信设备迁移

日期：2026-08-20  
状态：accepted

## 背景

Redmi Turbo（Android）是首个 Primary Vault，Windows 将作为 Secondary Trusted Device。系统需要在手机损坏、丢失或更换时恢复数据，同时保持 local-authoritative encrypted hybrid 的边界：Relay、运营方或单一服务端凭据不能单独解密完整 Vault。

只依赖设备迁移会在所有可信设备同时丢失时造成永久数据丢失；只依赖用户记忆的密码又容易受到低强度口令和服务端攻击。v1 必须在零知识边界、可操作性和明确的丢失风险之间作出可验证选择。

## 决定

1. v1 恢复采用两个互补入口：
   - **可信设备迁移**：优先入口。已解锁的 Primary/Secondary Trusted Device 通过带外确认，将必要的账户密钥材料安全封装给新设备；
   - **离线用户恢复包 + 恢复码**：无可用可信设备时的入口。加密恢复包与解锁它的高熵恢复码必须分离保管。
2. Relay 可以保存加密数据和加密恢复包，但不得同时持有足以解密恢复包的材料；登录密码、短信、邮箱验证或服务端重置均不能单独恢复完整 Vault。
3. v1 不采用服务端托管明文主密钥、服务端可单独解密的 escrow，或仅凭用户低熵登录密码派生 Vault Master Key。
4. 恢复包必须版本化并带完整性保护，至少包含恢复所需的账户/epoch 密钥封装、密钥 ID、算法与 Schema 版本；不得包含可直接使用的明文长期密钥。
5. 成功恢复后必须先验证包完整性、恢复码、账户身份与设备绑定，再导入密钥；随后同步撤销列表、最新 epoch、deletion tombstone 和密文数据，验证完成前不得开放业务读取。
6. 恢复材料更新、可信设备新增/撤销、恢复执行都必须产生可审计的本地安全事件，但日志不得记录恢复码或密钥材料。

## 生命周期规则

### 创建与验证

- 首次启用恢复时生成高熵恢复码和加密恢复包；恢复码由用户离线保存，应用不在 Relay 上保存可用副本；
- 用户必须完成一次恢复材料验证（例如重输指定部分或在隔离流程中验证完整恢复码）后，系统才标记为 `recovery_ready`；
- 未验证时 UI 必须明确显示“所有可信设备丢失将永久丢失数据”，不得把已生成等同于已可恢复。

### 轮换

- 新增或撤销 Trusted Device、怀疑恢复码泄露、恢复成功、密钥算法/格式升级时，必须生成新恢复包；
- 怀疑恢复码泄露时同时轮换其保护的恢复密钥；设备撤销还必须启动新的 Account Epoch；
- 旧恢复包进入 revoked 状态并尽快从 Relay/本地备份清除。轮换主要保护未来数据，不承诺让已泄露密钥访问过的历史密文重新保密。

### 撤销与设备丢失

- 可信设备撤销后不得获得新 epoch key；撤销不能远程抹掉该设备此前已经解密或导出的数据；
- 若手机丢失但 Windows Trusted Device 仍可用，优先用 Windows 迁移并撤销旧手机；
- 若全部 Trusted Device 丢失，必须同时拥有可用的加密数据备份、离线恢复包和对应恢复码；任一缺失或损坏都可能导致永久不可恢复。

### 备份分离

- **数据备份**包含加密事件、Blob、Schema/epoch 元数据、撤销与删除状态；
- **恢复包**只包含经过保护的密钥恢复材料；
- **恢复码**是独立的高熵秘密；
- 至少把恢复码与手机、数据备份、恢复包分开保管，避免单点失窃同时暴露数据与解密能力；不要求 v1 服务端了解其存放位置。

## 明确接受的风险

- 全部可信设备、加密数据备份、恢复包或恢复码的必要组合丢失时，数据永久不可恢复；项目方不能绕过该结果；
- 恢复码被窃且攻击者同时取得恢复包和密文备份时，Vault 可能被离线解密；因此恢复码必须高熵且分离保管；
- 设备撤销与恢复材料轮换不能收回攻击者在此前已经解密的数据；
- v1 不引入社交恢复、多方门限托管或企业管理员恢复，以避免在未验证核心流程前扩大攻击面。

## M2 验证与退出条件

此 ADR 只冻结策略，不表示功能已经实现。M2 退出前必须具备可审查的协议/测试设计，覆盖：

- Trusted Device 迁移以及无设备时的恢复包流程；
- 恢复包创建、完整性失败、错误恢复码、版本不兼容和重复恢复；
- 恢复材料验证、轮换、撤销与旧包拒绝；
- 恢复后先应用设备撤销和 deletion tombstone，再开放 Vault；
- Relay 或单一服务端凭据无法独立解密的威胁模型走查；
- Android Primary Vault 与 future Windows Trusted Device 的端到端实现验证计划。

真正的实现、跨端互操作和破坏性恢复演练在后续里程碑验收；未完成前不得宣称恢复能力可用。

## 后续候选

在 v1 经真实 dogfooding 后，再评估多份额/社交恢复、硬件密钥和更强的灾难恢复方案；任何候选都不得回退“服务端不能单独解密”的边界。
